## TL;DR

- 2026年9月にTypeSafe AIが発表した新モデル「Jev」を、既存の代表的なエンコーダモデルBERTと比較しながら整理します
- 両者は「自由形式のテキストを生成しない」という共通点を持ちますが、その理由も入出力の設計も大きく異なります
- 「分類に使うモデルだ」という単純な理解では両者とも捉えきれない、という点を掘り下げます

## 背景・課題

2026年9月15日、TypeSafe AIというスタートアップが「Jev」という新モデルを発表しました。元OpenAIでChatGPTとRLHFの開発に関わったDiego Almeida氏が創業し、シード資金40M$を調達しての発表です。

「文章を生成しないAIモデル」という触れ込みを見たとき、真っ先に頭に浮かんだのが2018年発表のBERTでした。BERTも自己回帰的な文章生成を行わないモデルだからです。両者は何が同じで何が違うのか、自分の理解を整理する目的でこの記事を書きます。

対象読者は、Transformerの基本構造や「事前学習・ファインチューニング」という概念をある程度知っている方を想定しています。

## 本文

### Jevとは何か——2026年9月に登場した「判断特化型」モデル

TypeSafeはJevを「the first System One model」と呼んでいます。チャットのように人と対話するためのモデルではなく、ソフトウェアの内部で高速に判断を下すためのモデルだという位置づけです。想定用途として、リクエストの振り分け、レコードのスコアリング、AI出力のジェイルブレイク検知などが挙げられています。応答速度は約100ミリ秒、価格は入力100万トークンあたり0.042ドル・出力は無料とされ、「一般的な生成LLM比で100倍高速・100倍安価」と謳われています（この価格・速度の数値は公式ブログではなく報道記事ベースであり、一次情報での明記は確認できていません＝未検証）。

### なぜ両方とも文章を生成しないのか——理由は同じではない

BERTとJevはどちらも自由形式の文章を自己回帰的に生成しませんが、その理由は異なります。

- **BERT**: 双方向Transformerのエンコーダのみの構造で、事前学習がMasked Language Modeling（文中の穴埋め）という設計だったため、そもそも逐次的にトークンを生成する能力を持つように作られていません。アーキテクチャ・訓練方法そのものに起因する制約です。
- **Jev**: Transformerベースであり、原理的には生成する能力を持たせることもできたはずです。しかしTypeSafeは意図的に生成をさせない設計を選んでいます。生成を放棄することで速度や型安全性を得る、という製品設計上の意図的な選択です。

同じ「生成しない」でも、BERTは「作れない」、Jevは「あえて作らせない」という違いがあります。

### 学習方法はどう違うのか——事前学習+ファインチューニング vs RLCD

BERTは自己教師あり事前学習（Masked Language Modeling + Next Sentence Prediction）を行った後、タスクごとに出力ヘッドを追加してラベル付きデータでファインチューニングする、という2段階の学習が基本です。

Jevは「Reinforcement Learning for Calibrated Decisions（RLCD）」という手法で学習されているとTypeSafeは説明しています。狙いは出力される確率が実際の結果頻度と一致するようキャリブレーションすることで、通常のRLHFが招きがちな「過度な自信・モード崩壊」を避けることを目的としているとのことです（具体的な損失関数などの詳細は非公開のため未検証です）。

### 入力は何が違うのか——「型付き質問」を読み解く

ここがBERTとJevの一番わかりやすい違いです。

**BERTの入力**は自然言語のトークン列そのものです。WordPieceでトークン化した文章を、先頭に`[CLS]`、文の区切りに`[SEP]`という特殊トークンを挟んで入力します。「何を答えてほしいか」は入力には書かれておらず、学習時に付け足したヘッド（分類層など）が決めます。抽出型QA（SQuAD形式）では`[CLS] 質問文 [SEP] 文章 [SEP]`のように質問文も入力に含めますが、それでも「答え方（スパン予測という形式）」はモデル構造側に固定されており、リクエストごとに変えることはできません。

**Jevの入力**は、公式ドキュメントの言葉を借りると `state`（判断対象のコンテキスト）と `typed questions`（型付き質問）の組み合わせです。「型付き質問」とは、質問の内容と同時に「答えの形式（型）」も指定する質問のことで、TypeSafeは3つのプリミティブを定義しています。

- **Choice**: "a System One question type for selecting one option from a defined set."（定義済みの選択肢から1つを選ぶ）
- **Score**: "a System One question type for rating content against ordered, descriptive levels."（順序付けられた記述的なレベルに対して評価する）
- **Noul**: "asks the TypeSafe model to evaluate a yes/no question and return the probability that the answer is yes."（Yes/No質問を評価し、Yesである確率を返す）

BERTのSQuAD形式の質問と本質的に違うのは、「答え方」を宣言する場所です。BERTでは答え方（分類なのかスパン予測なのか）がモデルの外側（学習済みのヘッド構造）に固定されているのに対し、Jevの型付き質問は答えの型そのものをリクエストの中で明示的に宣言します。またJevは複数の質問を並列・独立に評価でき、公式ドキュメントには「質問を追加しても応答時間はほとんど変わらない」という記述もあります。

### 「分類に使うモデル」という理解はどこが不正確か

両モデルとも「分類に使うモデルだ」と単純化すると実態より狭く括りすぎます。

- **BERT**: 分類（感情分析、固有表現抽出など）に加えて、分類に当てはまらない用途も広く使われます。抽出型QAは文章中の開始・終了位置を予測するタスクで、固定クラスから1つ選ぶ分類とは性質が異なりますし、文埋め込みを使った意味検索・類似度計算は教師なしの用途でカテゴリへの割り当てを行っていません。
- **Jev**: 3つのプリミティブのうち、Choiceは定義済みの選択肢から選ぶという点で分類そのものです。一方Noul（Yes/No確率）は分類というより**確率推定**、Scoreは順序付けられたレベルへの評価という点で分類ともまた違う性質を持ちます。

確率推定とは、「AかBか」を1つに決めて答える分類とは違い、「Aである確率は0.73」のように連続値の確率そのものを答えとして返すことです。分類モデルも内部的にはソフトマックスで確率を計算していますが、最終的にユーザーに渡すのは確率が一番高いクラスという離散的なラベルです。確率推定では、その確率の数値自体が最終成果物になります。良い確率推定の基準は的中率ではなく**キャリブレーション**、つまり「モデルが0.7と答えたケースを100件集めたとき、実際に真だったケースが約70件であるか」です。前述のRLCDの"Calibrated"は、まさにこの性質を訓練目的として最適化していることを指していると考えられます。

### 「100倍速く安い」という主張はBERTにも当てはまるのか

TypeSafeの「一般的な生成LLM比で100倍高速・100倍安価」という主張は、自己回帰的に文章を生成する従来のLLMとの比較です。BERTのような小型のエンコーダ専用モデル（BERT-baseで約1.1億パラメータ）は、そもそも1回のフォワードパスで完結し逐次的なトークン生成を行わないため、もともと生成型LLMより高速・安価です。つまりこの比較はBERTのようなモデルには当てはまらない、あるいは意味を持たない可能性が高いと考えられます（TypeSafe側の公表資料でBERT等との直接比較は確認できておらず、断定はできません）。

批判的に見ると、Jevは「BERTが元々得意だった効率的な単発判定」を、ファインチューニング不要・任意の質問定義に対応という形で再現・拡張しようとしている、という見方もできそうです。「生成LLMの手軽さ」と「BERTのような専用モデルの効率」の中間を狙った製品、という位置づけが妥当かもしれません（これは筆者の解釈であり、TypeSafeが公式にそう説明しているわけではありません）。

## 理解度チェック

自分の理解を確認したい方は、以下の問いに答えてから解答を開いてみてください。

:::details Q1. Jevは「LLMではない」とされますが、その根拠は何ですか？
Jevはあらかじめ決まった出力空間（Choice/Score/Noulの確率・選択肢・レベル）の中の値しか返さず、自由形式の自然文を生成しないためです。入力（state + typed questions）は柔軟ですが、LLMと区別されるのは出力側の制約です。
:::

:::details Q2. BERTとJevは、どちらも文章を生成しませんが、その理由は同じですか？
異なります。BERTはアーキテクチャ・訓練方法（エンコーダのみ、Masked Language Modeling）上、生成する能力を持つように作られていません。Jevは Transformer ベースで潜在的には生成可能なはずですが、速度・型安全性のためにあえて生成をさせない設計を選んでいます。
:::

:::details Q3. 「BERTは分類、Jevは確率推定」という理解は正確ですか？
不正確です。BERTは分類（感情分析、NER）に加え分類ではない用途（抽出型QA、埋め込みによる類似度計算）も持ちます。Jevも同様に、Choiceは分類的ですが、Noulは確率推定、Scoreは順序レベルの評価という異なる性質を持ちます。どちらも「分類だけ」では括れません。
:::

:::details Q4. BERTで答え方を変えたい場合と、Jevで答え方を変えたい場合、それぞれ何をする必要がありますか？
BERTは新しいタスク用の出力ヘッドを付け直し、ラベル付きデータで再学習（ファインチューニング）する必要があります。Jevはリクエストに含める型付き質問（Choice/Score/Noulの定義）を書き換えるだけで、モデル自体の再学習は不要です。答え方の定義がモデルの重みに焼き込まれているか、リクエスト側にあるか、という違いです。
:::

:::details Q5. Jevの「型付き質問」とは何ですか？BERTのSQuAD形式の質問と同じ仕組みですか？
型付き質問とは、質問の内容と同時に答えの形式（Choice/Score/Noulのどれか）も指定する質問です。BERTのSQuAD形式の質問はただの自然文で、答え方（スパン予測）はモデルの外側の学習済み構造が固定的に決めており、リクエスト側で変更できません。Jevは答えの型そのものをリクエスト内で宣言できる点が異なります。
:::

:::details Q6. BERTとJevの入力は、それぞれ何から構成されますか？
BERTはテキスト（トークン列）のみです。Jevは公式ドキュメントの言葉で言う「state（コンテキスト）」と「typed questions（型付き質問）」の組み合わせです。
:::

:::details Q7. 「Jevは100倍速く安い」という主張は、BERTのようなモデルにも当てはまりますか？
この主張は自己回帰的に文章を生成する従来のLLMとの比較であり、そもそも1回のフォワードパスで完結するBERTのような小型エンコーダモデルには当てはまらない可能性が高いと考えられます（公式資料での直接比較は確認できておらず未検証です）。
:::

## まとめ

- JevとBERTは「自由形式のテキストを生成しない」という共通点を持つが、その理由は「作れない（BERT）」と「あえて作らせない（Jev）」で異なる
- 入力の違いが本質：BERTはテキストのみ、Jevは`state`＋`typed questions`（Choice/Score/Noulという3プリミティブ）
- 「答え方」をどこで定義するか（モデルの重み vs リクエスト）が、ファインチューニングの要否を分ける
- どちらのモデルも「分類専用」ではなく、確率推定・順序評価・抽出など複数の性質を持つタスクを扱う
- 「100倍高速・安価」という主張は生成型LLMとの比較であり、BERTのような専用エンコーダモデルには当てはまらない可能性がある
