## TL;DR

- UXデザインの「ユーザーの本当のニーズを掘り下げる」思考は、エンジニアリングの「本当に必要な機能を見極める」思考と構造的に同じ
- BeRealの設計から「制約による誘導」という概念を学び、API設計やエラーハンドリングへの見方が変わった
- 「使いにくさの責任は製品側にある」という視点を持つことで、仕様を問い直す力が鍛えられる

## 背景・課題

新卒研修でUXデザインの講義を受けたとき、正直に言うと最初はピンときませんでした。「ユーザーのことを考える」「使いやすくする」——そんなの当たり前じゃないか、と思っていました。

この記事は、その「当たり前」という感覚がどのように覆されたか、そしてエンジニアとしての設計の見え方がどう変わったかを記録したものです。

**対象読者**: バックエンド・フロントエンドを問わず、「UXデザインはデザイナーの仕事」と思っているエンジニアの方

## 「当たり前を考える」ことの重要性

講義中、思わずこんな質問をしてしまいました。

> 「これ（UXデザイン）って、結局何が重要なんですか？」

返ってきた答えは、「その"当たり前"を考えることこそが重要なんです」というものでした。

ただ、そのときの私には、この答えがまったく腑に落ちませんでした。「当たり前を考える」とは具体的に何をすることなのか。それがなぜエンジニアである自分にも関係するのか。モヤモヤが残ったままだったので、自分で調べてみることにしました。

調べ始めた時点で、私はUXデザインを「画面を見やすく、使いやすく整えること」くらいにしか捉えていませんでした。デザイナーが具体的に何を考え、どんな順番で物事を決めているのか、まったくイメージできていなかったのです。

一般的に、UXデザインとは、ユーザーがサービスやアプリを通じて得る体験全体を設計することを指します。ユーザーを想定し、その人が本当に求めていることを捉えながら、サービスの形を決めていく営みです。

書籍を読んだり、UXデザインに詳しい知人に話を聞いたりしながら調べていく中で私が理解したのは、**デザイナーがやっているのは、人間を中心に据えて課題の解決方法を見つけ、「本当に必要なことは何か」を考えること**だということです。

これは、エンジニアが「どんな機能で解決するか」から考え始める視点とは異なるアプローチです。機能から考えると、作れるもの・作りたいものに引っ張られ、ユーザーに提供するものが本来の目的からずれてしまうことがあります。だからこそ、作るもの（提供するもの）がずれないようにするために、UXデザイン的な思考が必要なのだとわかりました。

そして、「本当に必要なことを見極める」という点では、エンジニアがMVP（Minimum Viable Product）を考えることにとても近いと感じています。職種は違っても考え方は似ていて、**UXデザインとエンジニアリングは別物ではない**——これが、自分で調べてみて理解した一番大きなことでした。

## 具体例から考える：BeRealの体験設計

概念として理解できても、具体的な事例を見るまではなかなか実感が持てませんでした。そこで参考にしたのが、書籍『はじめてのUXデザイン図鑑』です。身近なサービスを例にUXデザインを解説している本で、その中でも特に腹落ちしたのが、BeRealという写真SNSの体験設計でした。

今のSNSでは、加工したり映える写真を選んで投稿するのが当たり前になっています。しかしBeRealは、通知が来た瞬間にその場で撮影して投稿するという仕組みです。

これがうまくできている理由は、**あの唐突な通知そのものが、「加工する時間がなかった」「映える投稿じゃなくていい」という言い訳を、設計側があらかじめユーザーに用意している**からです。通知の唐突さは不便な仕様ではなく、ありのままを投稿させるための仕掛けでした。

エンジニアリングに置き換えると、これは**制約による誘導**です。バリデーションやAPIのインターフェースをあえて狭く設計することで、使い手が意図した通りの振る舞いしかできなくなる。

```typescript
// 例: 呼び出し側にミスをさせない型設計
type UserID = string & { readonly brand: unique symbol }

function getUser(id: UserID): User { ... }
// → 生のstringをそのまま渡せなくするブランド型
```

UIの「不便さ」も、意図して設計された制約であることがある——これは、エラーハンドリングやAPI設計で「呼び出し側にミスをさせない形」を考える発想と本質的に同じだと感じました。

## デザインを学んでわかったこと

デザインを学んで最も印象的だったのは、「使いにくいのはユーザーが悪いのではなく、製品（テクノロジー）側に責任がある」という視点です。

これはソフトウェア設計の文脈にも馴染みのある考え方です。バグや誤操作が起きたとき、「ユーザーが間違った使い方をした」と切り捨てるのではなく、「その誤操作を誘発する設計になっていたのはなぜか」を問う。

ボタンの配置や製品の形ひとつにも意味と文脈がある、という視点を持つようになってから、普段触っているUIの見え方が変わりました。デザインとは、人間という不確実性の高い相手と製品との対話であり、デザイナーはその橋渡しをする存在なのだと感じています。

## まとめ

- UXデザインは、人間を中心に「本当に必要なことは何か」を考えるアプローチであり、機能から解決策を考えるエンジニアの視点とは入り口が異なる
- それでも「本当に必要なことを見極める」点はMVPを考えることに近く、職種は違ってもUXデザインとエンジニアリングは別物ではない
- 使いにくさの責任を製品側に置く視点が、仕様を問い直す力につながる

機能から考えるクセのあるエンジニアにとって、「そもそも誰のための、何のためのものか」を人間起点で問い直すUXデザインの思考は、作るものがずれないための大切な支えになります。UXの視点を持つことは、単に見た目を整えるスキルではなく、**本当に必要なものを見極め、仕様を問い直す力**を鍛えることだと感じています。

「当たり前」を疑ってみると、世界の見え方が変わります。
