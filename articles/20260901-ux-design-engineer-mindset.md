## TL;DR

- UXデザインの「ユーザーの本当のニーズを掘り下げる」思考は、エンジニアリングの「本当に必要な機能を見極める」思考と構造的に同じ
- BeRealの設計から「制約による誘導」という概念を学び、API設計やエラーハンドリングへの見方が変わった
- 「使いにくさの責任は製品側にある」という視点を持つことで、仕様を問い直す力が鍛えられる

## 背景・課題

新卒研修でUXデザインの講義を受けたとき、正直に言うと最初はピンときませんでした。「ユーザーのことを考える」「使いやすくする」——そんなの当たり前じゃないか、と思っていました。

この記事は、その「当たり前」という感覚がどのように覆されたか、そしてエンジニアとしての設計の見え方がどう変わったかを記録したものです。

**対象読者**: バックエンド・フロントエンドを問わず、「UXデザインはデザイナーの仕事」と思っているエンジニアの方

## 「当たり前を考える」ことの重要性

講義中、思わずこんな質問をしてしまいました。

> 「これって、結局何が重要なんですか？」

返ってきた答えは、「その"当たり前"を考えることこそが重要なんです」というものでした。

UXデザインとは、ユーザーを想定してサービスやアプリを設計し、その過程でお客様の本当のニーズを捉えていく作業です。それは、開発においてMVP（Minimum Viable Product）がブレないようにするための土台になっています。

ここで気づいたのは、**UXの「ユーザーの本当のニーズは何か」を掘り下げる作業と、エンジニアの「本当に必要な機能は何か」を削ぎ落として見極める作業は、同じ問いを別の角度から扱っているだけ**だということです。

仕様を決める前に「そもそも誰のための、何のための機能か」を問い直す——エンジニアリングでも当然やっているはずのことなのに、UXという文脈で説明されると急に「当たり前」に聞こえてしまう。この構造に気づいたことで、一気に自分の言葉として理解できるようになりました。

## なぜBeRealの設計は優れているのか

概念として理解できても、具体的な事例を見るまではなかなか実感が持てませんでした。最も腹落ちした事例が、BeRealという写真SNSの体験設計です。

今のSNSでは、加工したり映える写真を選んで投稿するのが当たり前になっています。しかしBeRealは、通知が来た瞬間にその場で撮影して投稿するという仕組みです。

これがうまくできている理由は、**あの唐突な通知そのものが、「加工する時間がなかった」「映える投稿じゃなくていい」という言い訳を、設計側があらかじめユーザーに用意している**からです。通知の唐突さは不便な仕様ではなく、ありのままを投稿させるための仕掛けでした。

エンジニアリングに置き換えると、これは**制約による誘導**です。バリデーションやAPIのインターフェースをあえて狭く設計することで、使い手が意図した通りの振る舞いしかできなくなる。

```typescript
// 例: 呼び出し側にミスをさせない型設計
type UserID = string & { readonly brand: unique symbol }

function getUser(id: UserID): User { ... }
// → 生のstringをそのまま渡せなくするブランド型
```

UIの「不便さ」も、意図して設計された制約であることがある——これは、エラーハンドリングやAPI設計で「呼び出し側にミスをさせない形」を考える発想と本質的に同じだと感じました。

## 使いにくさの責任は製品側にある

デザインを学んで最も印象的だったのは、「使いにくいのはユーザーが悪いのではなく、製品（テクノロジー）側に責任がある」という視点です。

これはソフトウェア設計の文脈にも馴染みのある考え方です。バグや誤操作が起きたとき、「ユーザーが間違った使い方をした」と切り捨てるのではなく、「その誤操作を誘発する設計になっていたのはなぜか」を問う。

ボタンの配置や製品の形ひとつにも意味と文脈がある、という視点を持つようになってから、普段触っているUIの見え方が変わりました。デザインとは、人間という不確実性の高い相手と製品との対話であり、デザイナーはその橋渡しをする存在なのだと感じています。

## まとめ

- UXの「ユーザーの本当のニーズ」とエンジニアの「本当に必要な機能」は同じ問いの裏表
- 「制約による誘導」はAPI設計・型設計・バリデーション設計と同じ発想
- 使いにくさの責任を製品側に置く視点が、仕様を問い直す力につながる

技術的な視点に加えて、「この製品はどんな体験を提供したいのか」という視点が増えました。エンジニアとしてUXの視点を持つことは、単に見た目を整えるスキルではなく、**仕様を問い直す力**を鍛えることだと感じています。

「当たり前」を疑ってみると、世界の見え方が変わります。
